# 동호회 참가자 명단

구현일: 2026-11-24. PRD FR-02의 명단 관리 단계다. 동호회 상세의 **참가자 명단**에서 선택한 동호회만 조회한다. DB 스키마와 기존 사용자 데이터는 변경하지 않았다.

## 사용자 흐름

- 승인된 회원과 운영자는 활동·비활성 명단을 구분해 읽는다. 계정 연결 여부와 보조 라벨을 표시한다.
- 활동 중인 동호회의 운영자는 참가자를 추가하고 이름·보조 라벨·활동 여부를 수정한다. 일반 회원과 종료된 동호회의 운영자에게는 수정 버튼이 없다. 실제 권한은 서버가 요청마다 검사한다.
- 이름은 앞뒤 공백·줄바꿈 제거 후 **1~40 Unicode scalar**다. 실제 `club_participants_display_name_check`와 맞췄으며 프로필·게스트 닉네임 규칙과 혼동하지 않는다. 결합 문자·이모지는 여러 자로 계산될 수 있다.
- 동명이인을 허용한다. 보조 라벨은 선택이며 비우면 `NULL`로 저장한다. 서버에 라벨 길이 제약이 없어 앱도 임의 제한을 추가하지 않았다.
- 신규 참가자는 계정 없이 활동 상태로 등록한다. 이름만으로 회원 계정에 연결하지 않는다. 수정 요청에 `account_id`를 넣지 않아 기존 연결을 유지한다.
- 비활성화는 저장 전 확인을 받으며 삭제하지 않는다. 기존 참가자 UUID·경기 기록은 유지되고 다시 활성화할 수 있다. 계정 연결 충돌 등 서버 제약이 있으면 저장 실패로 안내한다.

## 조회·저장 계약

1. 현재 세션 UUID가 이 화면의 계정과 일치하는지 확인한다.
2. `club_participants`에서 `club_id`를 명시적으로 필터링하고 ID 순서로 200개씩 읽는다. 활동·비활성 행 모두 포함한다. 조회 전후 세션을 확인하고 다른 동호회 행·중복 UUID 응답은 거부한다.
3. 쓰기는 기존 `league_command` RPC의 `save_participant`만 사용한다. `club_id`, `display_name`, `label`, 수정 시 `participant_id`·`is_active`를 보낸다. 앱에 관리자 비밀 키를 추가하지 않는다.
4. RPC의 `participant_id` 응답을 확인하고 명단을 다시 읽는다. 대상 행의 UUID·이름·라벨·상태가 요청과 일치해야 저장 성공으로 표시한다. 재조회 전 기존 목록을 낙관적으로 변경하지 않는다.
5. 저장 응답 유실이나 재조회 실패 후 같은 요청을 재시도하면 같은 `request_id`를 사용한다. 내용이 바뀌면 새 ID를 쓴다. 이 보장은 `ClubRosterStore`가 유지되는 동안만 적용하며 앱 재실행 후 복구하는 영구 큐는 없다.

조회 실패 시 이전 명단을 제거하고 재시도를 제공한다. 저장 확인 실패 시 편집 내용을 유지하고 표시된 목록이 최신이 아닐 수 있음을 안내한다. 중복 제출과 저장 중 편집·시트 닫기를 막으며 취소된 작업은 결과를 화면에 반영하지 않는다. 운영자 수정 후 진행 중인 모임의 대진 갱신 필요 처리는 기존 서버 RPC가 담당한다.

## 검증과 남은 범위

원격 DB에서 이름 제약, 명단 읽기 RLS 및 실제 `save_participant` 함수 본문을 읽기 전용으로 확인했다. 회귀 검사는 이름 경계·JSON·라벨 지우기·계정 연결 보존·읽기 전용 역할·비활성화/재활성화·다른 동호회와 중복 응답 거부·재시도 ID·동시 요청·취소를 다룬다. 실제 Xcode 결과는 [검증 문서](xcode-verification.md)를 참고한다.

실제 사용자 JWT로 명단을 생성·수정하는 서버 왕복과 로그인 이후 화면의 시각·조작 검증은 별도 확인이 필요하다. 테스트는 mock 서비스 계약을 검증하며 실제 저장 성공을 증명하지 않는다. 회원 초대·가입 승인·계정 연결·인계·탈퇴, 모임 생성·참석·전적 화면 연동은 이번 범위에 포함하지 않는다. FR-02 전체 완료가 아니다.
