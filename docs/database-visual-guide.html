01

테이블을 눌러 연결을 따라가세요

선택한 테이블의 직접 연결만 표시합니다. 선은 참조 관계이며, 화살표 방향은 읽는 순서입니다.

선택한 테이블직접 연결된 테이블1 → N : 하나에 여러 개가 연결
선택한 테이블
clubs

클럽

모임과 참가자 명단을 묶는 공간입니다. 회원 권한도 클럽 단위로 구분됩니다.

주요 필드

  • id · 클럽 식별자
  • name · 클럽 이름
  • owner_account_id · 운영자 계정
  • status · 운영 상태

클럽 하나에 여러 회원·참가자·모임이 연결됩니다.

선택된 테이블은 Tab 키와 Enter/Space로도 바꿀 수 있습니다. ID는 사람 이름이 아니라 서로를 연결하는 고유 번호입니다. 상세 패널에는 그림에서 생략된 선택적 계정 연결도 표시합니다.

participant_stats

클럽 참가자 + 모임 참석 + 경기별 선수 + 완료 경기 + 유효 결과 → 승·패·승률
별도 집계 테이블이 아닌 조회용 뷰입니다. 이름이 같다는 이유만으로 기록을 합치지 않습니다.

02

‘민수’인데 왜 테이블이 세 개일까요?

같은 사람이라도 로그인, 클럽 기록, 모임 참석의 수명이 다르기 때문입니다.

로그인하는 나

계정

auth.users / profiles

앱에 로그인할 때 사용하는 신원입니다. 여러 클럽을 이용해도 계정은 같습니다.

민수의 계정account_id = U1
표시 이름: 민수
우리 클럽의 선수

클럽 참가자

club_participants

우리 클럽의 누적 전적을 쌓는 대상입니다. 앱에 가입하지 않아도 등록할 수 있습니다.

A클럽의 민수participant_id = P1
account_id = U1 또는 미연결
오늘 운동에 오는 나

모임 참석자

session_participants

토요일과 일요일의 참석 신청은 각각 별도 기록입니다. 경기에는 이 참석자 ID를 사용합니다.

토요일에 참석한 민수attendance_id = S1
club_participant_id = P1
참석: attending / 승인: approved

U1·P1·S1은 이해를 돕는 가상 ID입니다. attendance_id는 이 예시의 별칭이며 실제 컬럼명은 session_participants.id입니다. 실제 새 레코드는 UUID를 사용합니다.

게스트라면? 계정과 클럽 참가자 연결 없이 ‘이번 모임 참석자’만 만들 수 있습니다. 나중에 운영자가 클럽 참가자와 명시적으로 연결하면 그 참가자의 누적 전적에 포함됩니다. 가입 권한은 별도로 memberships가 관리합니다.
03

복식 한 경기가 전적이 되기까지

버튼을 눌러 결과 저장·정정·무효화의 차이를 확인하세요. 아래 전적은 이 예시 경기 한 건만 계산합니다.

1라운드 · 1번 코트

matches 1행 + match_players 4행

민수A팀 · 자리 1
지수A팀 · 자리 2
영희B팀 · 자리 1
철수B팀 · 자리 2

같은 사람의 중복 출전, 다른 모임 선수 연결, 팀별 인원 오류를 DB에서 검사합니다.

결과는 하나, 변경 이력은 별도

결과 정정 시 승패를 추가로 더하지 않습니다. 현재 유효한 결과를 다시 조회해 계산합니다.

아직 결과가 없습니다. 승패에 반영하지 않습니다.

이 경기의 전적 반영 예시
참가자승패승률
민수00—
지수00—
영희00—
철수00—
result_revisions: 변경 이력 없음
‘출전’과 ‘승패’는 다릅니다. 진행·완료·중단 경기는 출전 수에 포함되지만, 승패는 유효한 결과가 있는 완료 경기만 계산합니다. 완료 경기가 0이면 승률은 0%가 아니라 값 없음(NULL)입니다.
04

보이는 기록과 내부 관리 데이터를 분리합니다

public 스키마라는 이름이 ‘누구나 볼 수 있음’을 뜻하지는 않습니다.

private.invitations

회원 초대·모임 모집 링크의 만료와 폐기를 관리합니다. 토큰 원문 대신 해시를 저장합니다.

private.guest_sessions

개별 게스트 브라우저의 접근 권한입니다. 모집 링크와 분리되어 이미 승인된 게스트 권한을 별도로 유지·폐기합니다.

private.command_receipts

같은 요청이 다시 오면 기존 응답을 반환합니다. 저장 버튼 연타나 네트워크 재시도로 중복 처리되는 것을 방지합니다.

회원 조회 → 클럽별 RLS 검사 → 허용된 행만

승인된 소속을 기준으로 조회합니다. 프로필·가입 내역·결과 변경 이력에는 별도 제한이 적용됩니다.

변경 요청 → RPC → 권한·상태 검사 → 함께 저장

일반 앱 계정의 직접 INSERT/UPDATE/DELETE는 차단합니다. 승인·경기 시작·결과 변경은 트랜잭션과 잠금으로 처리합니다.

게스트 → 제한된 전용 RPC → 해당 모임 정보만

승인 전에는 안내와 자기 상태만, 승인 후에는 해당 모임의 허용된 이름·대진·결과를 제공합니다. 다른 클럽과 계정 ID는 노출하지 않습니다.

05

이렇게 나눈 이유

복잡해 보이는 분리는 실제 운영에서 서로 다른 것을 섞지 않기 위한 장치입니다.

이름 대신 ID로 연결하는 이유

동명이인과 닉네임 변경 때문에 이름을 식별자로 쓰면 다른 사람의 전적이 합쳐질 수 있습니다. ID로 연결하고, 이름은 표시용 값으로 취급합니다. 모임 참석자에는 당시 표시 이름도 저장합니다.

참석자가 바뀌면 기존 대진은 어떻게 되나요?

명단 버전(roster_version)을 올리고 대진을 재확인해야 한다고 표시합니다. 대진 확정 시 명단·대진 버전을 검사하므로 오래된 화면의 대진을 그대로 확정할 수 없습니다. 이미 시작된 경기의 선수 구성은 바꾸지 않습니다.

왜 선수 배열 대신 match_players를 두었나요?

경기마다 A팀 1·2번, B팀 1·2번을 각각 한 행으로 저장하면 참가자 외래 키, 중복 출전 방지, 팀별 두 명 검증을 DB에서 적용할 수 있습니다. 참가자별 출전과 전적 조회에도 같은 연결을 사용합니다.

테스트 데이터도 계속 보존해야 하나요?

아닙니다. 이전 이관은 사용자 데이터의 성격을 확정하지 못한 상태에서 삭제를 피한 조치였습니다. needs_owner·needs_review와 legacy_* 필드는 기존 자료 이관용이며 신규 운영 데이터의 정상 흐름이 아닙니다. 이 문서는 테스트 데이터를 초기화하지 않으며, 초기화 범위와 방법은 별도 작업입니다.

이 페이지가 실제 DB 상태를 보여주나요?

아닙니다. 저장소의 마이그레이션과 설계 문서를 바탕으로 만든 독립형 설명 페이지입니다. 실시간 DB 연결·로그인·데이터 저장 기능은 없고, 경기 시연도 브라우저 안의 예시입니다. 스키마 구현과 앱 전체 연동 완료는 구분해야 합니다.
