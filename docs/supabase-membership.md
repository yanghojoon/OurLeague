# 회원 초대·가입 승인·명단 연결

구현일: 2026-11-24. 기존 회원 초대 RPC를 iOS에 연결했다. 모임 게스트 초대와는 별개다. DB 스키마·RLS·사용자 데이터는 변경하지 않았다.

## 이용 순서

1. 운영자: 동호회 상세 → **회원 초대·가입 승인** → 초대 코드 발급 확인 → 공유 시트로 코드 전달.
2. 신청자: 로그인·프로필 등록 → 내 동호회 → **동호회 가입·승인 상태** → 64자리 코드 입력 → 가입 신청.
3. 신청자는 자기 계정 ID를 운영자에게 알려 본인을 확인한다. 승인 대기 화면에서도 자신의 계정 ID를 공유할 수 있다.
4. 운영자는 신청자의 계정 ID를 대조하고 가입 승인을 확인한다. 승인 전에는 신청자가 동호회 내부 데이터를 읽을 수 없다.
5. 가입 승인은 참가자 명단에 자동으로 사람을 추가하거나 연결하지 않는다. 운영자가 승인된 계정에서 **기존 참가자에 연결**을 열고 활동·계정 미연결 참가자를 선택해 한 번 더 확인한다. 이름만으로 연결하지 않는다.
6. 신청자는 가입 상태를 새로고침하고 창을 닫는다. 내 동호회 목록이 다시 조회되며 승인된 동호회를 선택할 수 있다. 실시간 알림은 없다.

현재 초대는 **공유한 코드를 앱에 직접 입력하는 방식**이다. 웹 초대 랜딩 페이지, Universal Link·자동 앱 진입은 구현하지 않았다. 가입 승인 취소·거절 및 명단 계정 연결 해제·교체 UI도 이번 범위가 아니다.

## 보안·개인정보 경계

- 기존 `profiles_read`는 본인 프로필만 허용한다. 신청자 이름을 보여주려고 다른 사람의 프로필 조회 권한을 늘리지 않았다. 운영자 화면은 기존 `memberships_read`가 허용하는 계정 UUID를 표시하고, 신청자의 이름·이메일을 추측하거나 가져오지 않는다.
- 자신의 승인 대기는 `memberships`만 조회한다. 승인 전 `clubs` 조인을 요청하지 않으며 이름 대신 동호회 UUID로 상태를 구분한다.
- 운영자는 현재 동호회 소속만 조회하고 승인된 운영자 행을 확인한다. 다른 클럽 행·중복 소속·잘못된 명단 응답을 거부한다. 앱의 역할 표시는 최종 권한이 아니며 RPC가 매번 권한을 검사한다.
- 계정 연결은 승인된 소속과 활동 중인 참가자에 한정한다. 앱은 조회 시점에 다른 계정에 연결된 참가자와 같은 계정의 두 번째 활동 참가자 연결을 거부한다. 서버 유일성 제약과 승인 확인도 유지한다. 조회 이후 동시 변경의 한계는 아래에 설명한다.
- 코드 원문은 메모리에만 두고 로그·UserDefaults·분석 이벤트에 저장하지 않는다. 입력은 보안 입력란이며 모델의 디버그 문자열은 코드를 가린다. 공유 시트와 텍스트 선택은 운영자가 명시적으로 코드를 전달할 때만 사용한다. 운영자가 공유한 코드의 복제본까지 앱이 회수할 수는 없다.

## RPC 계약과 실패 처리

| 기능 | 호출 | 확인 |
| --- | --- | --- |
| 발급 | `issue_invitation(target_club, target_session: NULL, expires_at)` | 24시간 뒤 시각 지정, 유효 토큰·만료 시각 확인 |
| 신청 | `league_command(request_membership, {token}, request_id)` | `membership_id`를 본인 소속 재조회에서 확인, pending/approved만 성공 |
| 승인 | `league_command(approve_membership, {club_id, membership_id}, request_id)` | 승인 응답 ID와 재조회 승인 상태 확인 |
| 명단 연결 | `league_command(save_participant, {club_id, participant_id, account_id}, request_id)` | 참가자 응답 ID와 재조회 계정 연결 확인, 이름·라벨·활동 상태는 요청에 넣지 않아 보존 |
| 폐기 | `league_command(revoke_invitation, {club_id, invitation_id}, request_id)` | `revoked: true` 확인 |

조회는 ID 순서로 200개씩 페이지를 읽고 세션 UUID를 전후 확인한다. 계정 전환 시 인증 루트가 화면 상태를 폐기한다. 가입·승인·연결은 재조회 전 성공으로 표시하지 않는다. 가입·승인·연결·폐기를 재시도할 때 동일 작업·본문에는 같은 요청 UUID를 재사용하며, 화면 store가 살아 있는 동안만 보장한다. 작업 취소 후에는 늦게 온 응답을 표시하지 않는다.

발급 RPC에는 요청 UUID가 없어 자동 재시도를 하지 않는다. 재발급은 기존 회원 초대를 폐기하므로 매번 확인을 받는다. 발급 응답 유실 시 기존 코드의 상태가 불확실함을 안내한다. 폐기를 시작하면 코드 원문을 숨기며 실패 시 같은 초대 ID로 폐기를 재시도할 수 있다. 만료 시 공유 코드를 숨긴다. 다른 기기의 재발급·폐기는 실시간 감지하지 않으며 서버가 사용 시 거부한다. 화면을 벗어나 코드를 잃어버리면 재발급하여 기존 코드를 무효화한다. 폐기·재발급이 이미 존재하는 신청과 승인을 취소하지는 않는다.

가입 승인과 계정 연결은 **서로 다른 트랜잭션**이다. 연결 실패가 이미 성공한 승인을 되돌리지 않는다. 수정된 참가자는 원래 UUID와 경기 기록을 유지하며 계정 간 기록을 자동 합치지 않는다.

계정 연결 직전에 소속·명단을 다시 조회해 다른 연결이나 소속 변경을 확인한다. 다만 기존 RPC에는 계정 연결의 예상 버전/이전 값 비교가 없다. 재조회와 쓰기 사이에 여러 기기가 같은 참가자의 연결을 동시에 바꾸는 충돌까지 원자적으로 막는 기능은 이번 범위에 없으며 후속 서버 계약 보강이 필요하다.

## 검증·남은 범위

원격 RPC와 RLS를 읽기 전용으로 확인했다. 토큰·JSON 계약, 만료, 자기 소속 검사, 승인 대기, 재수락 중복 방지, 요청 재시도 UUID, 비운영자 거부, 승인과 연결 분리, 잘못된 연결 거부, 초대 폐기 재시도, 동시 요청 억제에 대한 XCTest를 추가했다. [Xcode 검증 결과](xcode-verification.md)를 참고한다.

실제 두 Apple 계정의 초대·신청·승인·명단 연결 서버 왕복과 로그인 이후 화면 조작은 미검증이다. mock 검사는 실제 인증·RLS·저장 성공을 대신하지 않는다. 검증을 위해 원격에 초대나 테스트 사용자를 생성하지 않았다. 동호회 수정·탈퇴·운영자 인계, 모임·게스트 웹, 계정 삭제는 남아 있다. FR-02 전체 완료를 의미하지 않는다.
