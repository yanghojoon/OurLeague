# 내 동호회 조회·생성·선택

구현일: 2026-11-24. PRD FR-02의 첫 단계로 로그인·프로필 확인 다음에 실제 소속 동호회 목록을 연결했다. DB 스키마와 기존 데이터는 변경하지 않았다.

## 화면 흐름

```text
로그인 → 프로필 확인 → 내 동호회
  ├─ 승인된 소속 있음 → 선택 → 이름·소개·내 역할·상태 확인
  │                         └─ 다른 동호회 선택 → 목록
  ├─ 소속 없음 → 빈 상태 안내
  ├─ 새 동호회 → 이름·소개 입력 → RPC 생성 → 운영자 소속 재조회 → 상세
  └─ 조회 실패 → 오류·재시도
```

- 기존 녹색 강조색과 시스템 글꼴을 유지한다. 목록에서 운영자/회원 역할을 구분하며 생성은 별도 시트에서 진행한다.
- 동호회 이름은 앞뒤 공백·줄바꿈 제거 후 1~100 Unicode scalar로 검사한다. 결합 문자와 이모지는 여러 자로 계산될 수 있다. 이름 중복을 허용하고 UUID로 식별한다. 소개는 선택이며 서버에 별도 길이 제약이 없어 앱도 임의 제한을 추가하지 않았다.
- 승인 대기·비활성 소속은 목록에 포함하지 않는다. 종료된 동호회는 상태를 표시하며 운영 가능한 동호회로 취급하지 않는다.
- 목록 새로고침은 이전 선택과 데이터를 먼저 제거한다. 실패한 조회를 빈 목록으로 오인하지 않으며, 로그아웃·계정 전환 시 기존 루트와 소속 상태를 폐기한다.

## Supabase 계약

- [Swift select](https://supabase.com/docs/reference/swift/select)를 사용해 `memberships`와 외래키로 연결된 `clubs`를 한 요청에 조회한다. `account_id`는 현재 로그인 UUID, `status`는 `approved`로 필터링하고 소속 UUID 순서로 200개씩 페이지를 읽는다.
- 실제 `memberships_read` RLS는 본인 소속 또는 해당 클럽 운영자에게 읽기를 허용한다. 운영자가 다른 회원의 소속을 읽을 수 있으므로 앱의 본인 ID 필터도 유지한다. `clubs_read`는 `private.can_read_club`로 승인된 본인 소속을 요구한다.
- 소속 계정 ID, 승인 상태, 소속-클럽 UUID 일치와 목록 중복 여부를 검사한다. 클럽 조인이 없거나 권한상 가려진 경우 디코딩 실패로 처리한다. 역할은 클럽별로 유지하며 전역 운영자 권한을 만들지 않는다.
- 생성은 기존 `league_command(operation: create_club, payload: {name, description}, request_id: UUID)`만 사용한다. 서버는 `auth.uid()`로 클럽 운영자를 지정하고 승인된 운영자 소속을 같은 트랜잭션에서 생성한다. 앱에서 owner UUID를 요청 payload로 보내지 않는다.
- RPC 응답의 운영자·활동 상태를 확인한 뒤 소속을 다시 조회한다. 해당 클럽의 승인된 운영자 소속까지 확인되어야 생성 성공으로 표시한다.
- 응답 유실이나 생성 후 재조회 실패 시 동일한 내용에는 같은 요청 UUID를 재사용한다. 화면의 `ClubStore`가 유지되는 동안 서버 receipt로 중복 생성을 방지한다. 이름이나 소개를 바꾸면 새로운 명령이며, 앱 종료 후 요청 ID를 복원하는 영구 큐는 없다.
- 표시된 역할은 UI 상태일 뿐 권한 부여 수단이 아니다. 현재 소속 변경의 실시간 감지는 없으며 최신 목록은 새로고침으로 확인한다. 후속 데이터 작업은 서버에서 매번 권한을 검사해야 한다.

## 검증과 한계

- 기존 테스트 파일에 회귀 검사 20개를 추가했다. 빈 목록·조회 재시도·설정 실패·복수 클럽 역할 및 선택·갱신 실패 시 이전 데이터 제거·다른 계정/미승인/불일치/중복 소속 거부·JSON 계약과 길이·생성 확인·재시도 UUID·중복 요청·작업 취소를 확인한다.
- Foundation·Combine 기반 계약 실행으로 기존 검사 포함 63개를 검증한다. 실제 프로젝트의 제약, RLS 및 생성 RPC 계약은 읽기 전용 SQL로 확인했다. 서버 검증용 동호회나 사용자 데이터를 임의로 생성하지 않았다.
- 후속 [Xcode 검증](xcode-verification.md)에서 실제 SDK를 포함한 시뮬레이터 빌드와 XCTest 63개·로그인 UI 검사 1개를 통과했다. 실제 사용자 JWT를 통한 REST 조인·RPC 왕복과 동호회 화면의 시각 검증은 아직 하지 않았다. mock 검사는 실제 서버 저장 성공을 증명하지 않는다.
- 실기기에서 빈 계정의 첫 생성, 복수 동호회 생성·전환, 운영자/회원 구분, 오프라인 조회·생성 재시도, 로그아웃·계정 전환을 확인해야 한다.

## 다음 범위

회원 초대 수락·가입 승인, 명단 관리, 동호회 수정·탈퇴·운영자 인계, 모임과 실제 경기 연동은 아직 구현하지 않았다. 동호회 상세는 연결된 이름·소개·소속 상태만 표시한다. 이전 로컬 `GameMakerView`를 클럽 데이터 화면으로 오인하지 않도록 로그인 진입 경로에서 분리했으며, 기존 프로토타입 소스는 보존했다. FR-02 전체 완료를 의미하지 않는다.
